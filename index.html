How to Use

ハンズオンプロンプト集

AIでつくる簡易BIダッシュボードのハンズオンで使う、コピペ用のプロンプト集です。各ページのコードブロック右上の「コピー」ボタンを押して、AIチャットに貼り付けてください。

01 可視化の検討

データ説明文を貼り、AIと壁打ちしながら要件を固めます。

02 デザイン

見た目を相談し、要件+デザインを設計仕様書にまとめます。

03 実装

新しいスレッドに設計仕様書を貼り、単一HTMLを作らせます。

THREAD

スレッドの使い分け:ステップ1・2は同じスレッド、ステップ3は新しいスレッドで進めてください。

Dataset A

データ説明文 — 問い合わせ(データA)

問い合わせ対応ログを選んだ方は、このブロックをコピーして、ステップ1のプロンプトの「データ説明文を貼る」の部分に貼り付けてください。

Data Description — A 
問い合わせ対応のログ(CSV)

# 粒度
1行 = 1件の問い合わせ(チケット)。全23列。

# 列の定義
| 列名 | 形式 | 内容・値の範囲 |
| --- | --- | --- |
| 問い合わせID | 文字列 | 例: INQ-202504-00012(年月+通番)。一意。 |
| 受付日時 | 日時(YYYY-MM-DD HH:MM) | 問い合わせを受けた日時。全行に必ず入る。 |
| 初回応答日時 | 日時 または 空 | 担当者の初回対応日時。空欄=まだ応答していない(ステータス=受付)。受付日時より後。 |
| 解決日時 | 日時 または 空 | 解決日時。空欄=まだ解決していない(ステータス≠解決/クローズ)。初回応答日時より後。 |
| チャネル | カテゴリ | 電話 / メール / チャット / Web |
| 製品 | カテゴリ | スマート勤怠 / クラウド経費 |
| カテゴリ | カテゴリ | 使い方 / 不具合 / 仕様確認 / 請求 / 要望 |
| 中分類 | カテゴリ | カテゴリの下位区分(例: 使い方→初期設定/操作方法/権限設定/データ移行) |
| 問い合わせ種別 | カテゴリ | 質問 / クレーム / 要望 / 障害報告 |
| 優先度番号 | 整数(int) | 1=高 / 2=中 / 3=低(「優先度」とペア) |
| 優先度 | カテゴリ | 高 / 中 / 低 |
| 顧客区分 | カテゴリ | 大企業 / 中小 / 個人事業主 |
| ステータス番号 | 整数(int) | 1=受付 / 2=対応中 / 3=保留 / 4=解決 / 5=クローズ |
| ステータス | カテゴリ | 受付 / 対応中 / 保留 / 解決 / クローズ(番号とペア) |
| フェーズ番号 | 整数(int) | 1=受付 / 2=一次対応 / 3=エスカレ / 4=解決 / 5=完了 |
| フェーズ | カテゴリ | 上記の名称(番号とペア)。ステータスに沿って進む。 |
| エスカレ有無 | 整数(0/1) | 1=上位チームへエスカレ。不具合・障害報告で1になりやすい。 |
| 再オープン有無 | 整数(0/1) | 1=一度解決した件を再オープン(解決/クローズのみ1になりうる)。 |
| 対応チーム | カテゴリ | 一次窓口 / 技術サポート / 品質保証 |
| 担当者 | 文字列 | 担当者名(チームに属する)。 |
| 満足度 | 整数(int, 1〜5) または 空 | 顧客評価。空欄=未評価(解決/クローズのみ設定)。 |
| 件名 | 文字列 | 問い合わせの短い件名。 |
| 自由記述 | 文字列 | 自由文(顧客の声など)。 |

# 留意点
- 直近の月ほど「未解決(受付/対応中/保留)」が残る。古いものは概ね解決/クローズ済み。
- 番号列と名称列は常にペア(同じ番号=同じ名称)。
- 応答時間(=初回応答日時−受付日時)・処理時間(=解決日時−受付日時)は列に無い。必要なら算出する。
Dataset B

データ説明文 — 商談(データB)

商談パイプラインを選んだ方は、このブロックをコピーして、ステップ1のプロンプトの「データ説明文を貼る」の部分に貼り付けてください。

Data Description — B 
商談(案件)パイプラインのデータ(CSV)

# 粒度
1行 = 1件の商談(案件/オポチュニティ)。全22列。

# 列の定義
| 列名 | 形式 | 内容・値の範囲 |
| --- | --- | --- |
| 商談ID | 文字列 | 例: OPP-202504-00012(年月+通番)。一意。 |
| 顧客企業名 | 文字列 | 顧客の法人名。同じ企業が複数商談を持つ(マスタ的な軸)。 |
| 商談発生日 | 日付(YYYY-MM-DD) | 商談が立ち上がった日。全行に必ず入る。 |
| クローズ日 | 日付 または 空 | 受注/失注で確定した日。空欄=未クローズ(進行中/保留)。発生日以降。 |
| 最終活動日 | 日付 | 最後の活動日。発生日以降、クローズ日以前(クローズ済みの場合)。 |
| 業種 | カテゴリ | 製造 / 流通 / 金融 / 公共 / IT |
| 製品 | カテゴリ | スマート勤怠 / クラウド経費 / 統合ダッシュボード |
| 商談区分 | カテゴリ | 新規 / 既存深耕 / 更新 |
| リード獲得元 | カテゴリ | 展示会 / 紹介 / Web / インバウンド |
| エリア | カテゴリ | 関東 / 関西 / 中部 / 九州 |
| 企業規模 | カテゴリ | 大企業 / 中堅 / 中小 |
| ステージ番号 | 整数(int) | 1=リード / 2=ヒアリング / 3=提案 / 4=見積 / 5=最終交渉 / 6=クロージング |
| ステージ | カテゴリ | 上記の名称(番号とペア)。進行段階。 |
| ステータス番号 | 整数(int) | 1=進行中 / 2=受注 / 3=失注 / 4=保留 |
| ステータス | カテゴリ | 進行中 / 受注 / 失注 / 保留(番号とペア)。 |
| 受注確度 | 整数(int, 0〜100, %) | 受注=100、失注=0、進行中はステージに応じて10〜80。 |
| 失注理由 | カテゴリ または 空 | 価格 / 競合 / 時期 / 予算 / 要件不一致。空欄=失注以外。 |
| 営業チーム | カテゴリ | 第一営業部 / 西日本営業部 |
| 営業担当 | 文字列 | 担当者名(チームに属する)。 |
| 金額 | 整数(int, 円) | 案件金額。1万円単位(10000の倍数)。企業規模に応じて概ね30万〜1,200万円。 |
| 商談名 | 文字列 | 案件名。 |
| 次のアクション | 文字列 または 空 | 次のTodo。空欄=受注/失注(クローズ済み)。 |

# 留意点
- 直近の月ほど「未クローズ(進行中/保留)」が残る。古いものは概ね受注/失注済み。
- 番号列と名称列は常にペア(同じ番号=同じ名称)。
- 加重金額(=金額×受注確度)・商談日数(=クローズ日−発生日)は列に無い。必要なら算出する。
Dataset C

データ説明文 — 塗料の配合実験(データC)

塗料コーティングの試作実験データを選んだ方は、このブロックをコピーして、ステップ1のプロンプトの「データ説明文を貼る」の部分に貼り付けてください。

Data Description — C 
塗料コーティングの試作実験データ(CSV)

# 粒度
1行 = 1件の試作(配合レシピ×塗装条件の1組み合わせ)。全25列。
同じレシピIDが複数の試作に登場する(1つのレシピを複数の条件で試している)。

# 列の定義
| 列名 | 形式 | 内容・値の範囲 |
| --- | --- | --- |
| 試作ID | 文字列 | 例: TRIAL-202504-00012(年月+通番)。一意。 |
| 実験日 | 日付(YYYY-MM-DD) | 試作した日。全行に必ず入る。 |
| 開発テーマ | カテゴリ | 外装用耐候 / 金属防食 / 屋内意匠 / 水回り用 |
| レシピID | 文字列 | RCP-01〜RCP-28。同じIDなら配合6列(ベース樹脂〜添加剤)は必ず同じ値。 |
| ベース樹脂 | カテゴリ | アクリル / エポキシ / ウレタン / シリコン変性 |
| 溶剤系 | カテゴリ | 水系 / 溶剤系 |
| 顔料種 | カテゴリ | 酸化チタン / カーボンブラック / 酸化鉄 / 有機顔料 |
| 顔料濃度 | 整数(%) | 10〜45。配合中の顔料の割合。 |
| 架橋剤量 | 小数(%) | 0.0〜10.0(0.5刻み)。 |
| 添加剤 | カテゴリ | 分散剤 / 消泡剤 / レベリング剤 / なし |
| 下地処理 | カテゴリ | なし / 脱脂 / プライマー / ブラスト |
| 膜厚 | 整数(μm) | 15〜120(5刻み)。 |
| 乾燥温度 | 整数(℃) | 20〜140(5刻み)。 |
| 乾燥時間 | 整数(分) | 10〜120(10刻み)。 |
| ステータス番号 | 整数(int) | 1=試作済 / 2=試験中 / 3=評価完了 / 4=中止 |
| ステータス | カテゴリ | 上記の名称(番号とペア)。 |
| 冷熱サイクル数 | 整数(回) または 空 | -30℃⇔80℃を1サイクルとし、異常が出るまでの回数。500回で打ち切るため500は「完走・異常なし」。10刻み。評価完了のみ入る。 |
| 硬度番号 | 整数 または 空 | 1〜8(鉛筆硬度とペア)。 |
| 鉛筆硬度 | カテゴリ または 空 | 1=2B / 2=B / 3=HB / 4=F / 5=H / 6=2H / 7=3H / 8=4H |
| 光沢度 | 小数(GU) または 空 | 60度光沢。5.0〜98.0。 |
| 耐水試験日数 | 整数(日) または 空 | 7 / 14 / 30 / 60。試験に投入した場合のみ。 |
| 耐水性評価番号 | 整数 または 空 | 1〜5。 |
| 耐水性評価 | カテゴリ または 空 | 1=剥離 / 2=白化 / 3=わずかな変化 / 4=ほぼ変化なし / 5=異常なし(番号とペア)。評価完了のみ入る。 |
| 実験担当者 | 文字列 | 試作を担当した開発メンバー名。 |
| 備考 | 文字列 または 空 | 結果の所見や中止理由の自由記述。 |

# 留意点
- 空欄には2つの意味がある。「試作済」「中止」は測定値がすべて空欄、「試験中」は硬度・光沢だけ入り、冷熱サイクル数と耐水性評価が空欄。
- 冷熱サイクル試験は数ヶ月かかるため、直近の試作ほど「試験中」で結果が出ていない。
- 番号列と名称列は常にペア(同じ番号=同じ名称)。
- 乾燥熱量(=乾燥温度×乾燥時間)・耐久と耐水性の両立スコア・レシピ別の平均やばらつきは列に無い。必要なら算出する。
- 物性は互いにトレードオフの関係にある。1つの指標だけを最大化しても良い配合にはならない。
Step 1 — 壁打ち

ステップ1:可視化の検討 (壁打ち)

目的:どんな指標・グラフにするかをAIと相談し、要件を固めます。選んだデータのデータ説明文(前のページ)を「データ説明文を貼る」の部分に貼り付けてください。

Prompt — Step 1 
あなたはBI(ダッシュボード)設計の専門家です。私と一緒に、業務データを可視化するダッシュボードの要件を決めてください。

# 私のデータ(説明文)
（ここに上の「データ説明文」を貼る）

# 私の目的・見たいこと（空欄でもOK。書ける分だけ書くと、より自分ごとになります）
- 目的（何のために見る？）:（例: 月次レビューで現状を把握し、翌月の打ち手を決めたい）
- 見たい可視化・指標:（例: 月次の推移 / 内訳 / 担当者ごとの負荷 / 前月比）
- 重視したい観点:（例: 継続案件の偏り / 増減の兆し / 担当者の得意・苦手）
- 欲しい機能・操作:（例: 明細テーブルを担当者・状況で絞れる / 棒グラフをクリックすると他のグラフも連動して絞り込まれる(クロスフィルタ) / カテゴリ→中分類へドリルダウン）

# お願い
- 私の目的を引き出す質問をしながら、載せるべきKPI・グラフ・操作(クロスフィルタなど)を一緒に要件化してください。
- やり取りの結果を、「何を作るか」の要件として整理していきます。
- コードは生成せず、不明点が明らかになったタイミングで要件のみを出力してください。

# 進め方の方針(重要)
- いきなり大きなダッシュボードを設計しないでください。まず「最小構成(コア)」を提案してください。
- コアの目安は、KPIカード2〜3個 + グラフ2〜3個 + 明細テーブル1つ程度までです。
- 私がたくさん要望を挙げた場合も、「まず作るコア」と「後から足す拡張案」に必ず分けて整理してください。
- 各項目について「これは最初から本当に必要か?」を一度問い返してください。
- 迷ったときは、機能を足す方向ではなく減らす方向で提案してください。

# 必ず守る制約
- 出力は単一のHTMLファイル1つで完結(CSSやJSに分割しない)。
- CSVはセキュリティ(CORS/ローカルファイル制限)のため、ファイル選択ボタンとドラッグ&ドロップで手動アップロードする方式にする(自動読み込みはしない)。
POINT

まずは最小構成のシンプルなものを目指しましょう。最初から多機能にすると、エラーが多く発生して修正が大変になりがちです。最低限必要なものから作り、欲しい機能は後から追加するか、別のダッシュボードに分けて作ることを検討してください。

Step 2 — 設計

ステップ2:デザイン → 設計仕様書

目的:見た目を相談し、ここまでの要件とデザインを1つの「設計仕様書」にまとめます。ステップ1と同じスレッドで続けてください。

Prompt — Step 2 
次にデザイン(レイアウト・配色・KPIの並び)も相談させてください。
決まったら、これまでの内容(要件 + デザイン)を1つの「設計仕様書」にまとめ、コードブロックで出力してください。
コードは絶対に生成しないでください

# デザインの希望（空欄でもOK。あるとイメージに近づきます）
- 雰囲気・トーン:（例: シンプルで標準的 / 落ち着いた誌面風 / ダーク / ポップ 等）
- 配色:（例: ネイビー基調 / 暖色系 / モノクロ / 自社カラー 等）
- レイアウトの希望:（例: KPIを上部に並べる / グラフは2段 / 明細は下 等）
- 見せ方のこだわり:（例: 数字を大きく / 余白を広め / 各グラフにタイトル 等）


# 範囲の方針(重要)
- 設計仕様書には「最小構成(コア)」だけを記載してください。
- 拡張したい項目は「発展案(今回は実装しない)」として、仕様書の末尾に分けて箇条書きしてください。
- デザインも凝りすぎず、標準的で破綻しにくい構成を優先してください。

設計仕様書には、次の制約を必ず含めてください:
- 単一のHTMLファイル1つ(CSS/JS分割なし)
- Chart.jsとPapaParseをCDNで読み込む
- CSVは手動アップロード(ファイル選択+ドラッグ&ドロップ)
- 出力は全文を1つのコードブロックで
Step 3 — 実装

ステップ3:実装 (新規スレッド)

目的:まっさらな新しいスレッドで、設計仕様書とデータ説明文から一気に作らせます。

Prompt — Step 3 
次の仕様で、単一HTMLで動くBIダッシュボードを作ってください。出力はコピペできるよう、全文を1つのコードブロックで出してください。

# 設計仕様書
(ここにステップ2で作成した設計仕様書を貼る)
# 使用データ
（ここに上の「データ説明文」を貼る）

# 制約
- 単一のHTMLファイル1つ。CSSやJSに分割しない。
- Chart.jsとPapaParseはCDNで読み込む。
- CSVはファイル選択ボタン+ドラッグ&ドロップで手動読み込み。自動では読み込まない。
- F12(開発者ツール)を開かなくても状態が分かるよう、**エラーは画面上に分かりやすい日本語で表示**(Consoleだけに出さない)。読み込み失敗・必須列の欠落・データ空などで、修正するAIエージェントに何を伝えればよいか分かるメッセージを出すこと。
- 設計仕様書に書かれた機能だけを実装してください。気を利かせて機能を追加しないでください。
- 「発展案」と書かれた項目は実装しないでください。
- 動くことを最優先し、凝った演出やアニメーションは入れないでください。

保存して開く:コードブロックを 〇〇.html として保存 → ダブルクリックでブラウザで開く → 画面のボタン/ドロップからCSVを読み込む。

Glossary

付録:用語集

初心者向けの技術用語です。壁打ち中に分からない言葉が出てきたら、このページを開いてください。

HTML

ウェブページを作る言語(ファイルの拡張子は .html)。Chrome等のブラウザで開くと画面が表示される。今回のBIはこのファイル1つで動く。

CSS

HTMLの「見た目」(色・文字の大きさ・配置)を指定する仕組み。

JavaScript(JS)

HTMLに「動き」を与えるプログラム言語。ボタンを押した時の動作やグラフ描画などを担う。今回のBIでも使われる。

Markdown

簡単な記号(#・-・| 等)で見出し・箇条書き・表を書けるテキストの書式。このプロンプト集もMarkdown。AIチャットに貼ると整形されて表示される。

CSV

表データをカンマ(,)区切りで保存したファイル(拡張子 .csv)。Excel等でも開ける。今回のデータA/B/Cはこの形式。

CDN

便利なプログラムの部品(ライブラリ)を、ネット経由で読み込んで使う仕組み。ファイルを手元に用意しなくて済む。

Chart.js

折れ線・棒・円などのグラフを手軽に描ける無料の部品。AIがHTMLに組み込んで使う。

PapaParse

CSVを読み込み、プログラムで扱いやすい形に変換する無料の部品。

F12 / 開発者ツール

ブラウザの機能で、画面の裏側(エラーやプログラム)を確認できる。キーボードのF12キーで開く。

Console(コンソール)

開発者ツール内の画面で、エラー等のメッセージが出る場所。画面が真っ白になった時の原因確認に使う。

CORS

ブラウザのセキュリティ決まりの1つ。ローカルのHTMLが勝手にファイルを読むのを止める。だからCSVは「手動で選んで」読み込ませる必要がある。
